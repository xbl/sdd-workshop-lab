# 限额活动报名练习 · 项目原则

## 先确认规格

用业务目标、规则、异常和可观察的验收用例写清需要支持的行为。有疑问时向讲师确认，并把答复写进规格。学员评审确认 `spec.md` 后再做技术方案和任务拆分。计划和任务应能追溯到已确认的规则。

## 架构选择与实现边界

本项目预置了纯前端/纯内存起点（`index.html`、`page.js`、`registration.js`），同时**不限制技术栈与前后端架构**：

1. **纯前端/纯内存方式**：直接在 `registration.js` 与 `page.js` 中操作内存 `state`（初始含 `capacity`、`closed`、`registrations`，可按规格扩展），无需启动服务器即可打开 `index.html` 在单窗口内输入不同学员姓名测试；如需多窗口共享状态，可使用浏览器共享存储或改为后端服务。
2. **前后端/服务端方式**：可根据需要在方案中引入本地后端服务、API 接口与服务端存储/内存管理，并将 `index.html`、`page.js` 中的提交与调试配置（「设置名额」「截止报名」「重新开启报名」「清空报名」）真实接入后端，以便通过多个浏览器窗口直接测试并发与名额争抢。
3. **对齐契约**：无论采用哪种架构，界面操作与业务状态（名额限制、截止/开启、清空报名）必须前后端一致、无假数据敷衍。

## 让验证可复现

所有核心规则与边界场景均需有可重复执行的自动化测试（如 Node.js 原生测试 `node --test` 或所选框架的测试命令），并说明启动和验证方式。保留规格、任务和实际执行状态，供课堂回看。
